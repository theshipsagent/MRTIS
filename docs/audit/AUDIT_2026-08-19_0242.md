## 0. Executive summary

Seven claims were tested adversarially — each assumed wrong until the data
proved otherwise. **Three are confirmed exactly, one is confirmed with a
caveat, and three are wrong.**

The pipeline's mechanical core is sound: it is fully deterministic and
idempotent, the FGIS rollup conserves tonnage to the last kilogram, and the
"no fuzzy matching" discipline is genuinely absolute — there is no
edit-distance code anywhere in the codebase.

The failures are all of one kind: **rules that resolve identity or money by
vessel *name* rather than by IMO, and documentation that has drifted ahead of
the code.** One corrupted-IMO merge is provably wrong and injects a Baton
Rouge workboat's entire 2019 history into a real ocean tanker. The agency-fee
rule charges per berth departure rather than per port call, which puts 19.2%
of the headline revenue figure in question and contradicts the project's own
evidence document. And at least four genuinely commercial vessels sit on the
non-commercial exclusion list.

## 1. Method

### 1.1 Environment

The existing `.venv` (Python 3.11.15, duckdb 1.5.5, pandas 3.0.5) was reused.
To honour the read-only constraint while still performing the requested full
rebuild, the audit ran against an isolated copy:

- `scripts/`, `sql/`, `dictionaries/`, `docs/` and `data/db/mrtis.duckdb`
  were **copied** into a scratch directory
- The 36 `Zone Report*.csv` files and `fgis_source/` were **symlinked**
  (read-only inputs)
- All three build scripts were then run inside that copy

Post-audit verification confirmed byte-identical checksums on all six audited
code/schema files and all three audited dictionaries, and a clean `git status`
for every tracked path.

### 1.2 Builds performed

| Build | Purpose |
|---|---|
| Baseline (default flags) | Reproduce the published state |
| Second full rebuild | Idempotency check |
| `--keep-dredges` | Behaviour of the documented retention flag |
| `--zone-facility-path` missing | Dictionary-absence failure mode |
| `--vessel-type-path` missing | Dictionary-absence failure mode |

### 1.3 Verification approach

Each claim was attacked from the data side rather than read from the code:
counts recomputed from the raw CSVs, cross-reference integrity tested by
independent SQL, merge decisions re-derived from raw row profiles (draft,
agent, type, zone, river mile, action mix), and pure functions probed directly
with `NaN`/`None` in every argument position.

## 2. Claim 1 — Match rate — **CONFIRMED**

> *99.27% of in-coverage FGIS records matched; 1 ambiguous; 0 guesses.*

### Measured

| `match_status` | Records |
|---|---|
| `matched` | 12,445 |
| `unmatched_no_candidate` | 91 |
| `unmatched_ambiguous` | 1 |
| `unmatched_outside_coverage` | 1,991 |
| **Total** | **14,528** |

In-coverage = 12,445 + 91 + 1 = **12,537**.
12,445 / 12,537 = **99.2662% → 99.27%.** Confirmed.

### "0 guesses" tested three ways

| Test | Result |
|---|---|
| Records with a `vessel_key` but `match_status <> 'matched'` | **0** |
| Matched records with NULL `vessel_key` or NULL `mrtis_event_key` | **0** |
| Unmatched records absent from the review CSV | **0** (2,083 = 1,991 + 91 + 1) |

The single ambiguous record is `UNMATCHED-AQUITANIA-20241013` — 3 certificate
lines, 67,442 MT, corn and wheat to Mexico and Panama. This is precisely the
two-real-ships-share-a-name case the design exists to refuse, and it was
refused rather than guessed. That is strong corroborating evidence for
Claims 2 and 3 as well.

### Caveat — identity is never guessed, but event selection is

Vessel identity is never guessed. **Event** selection sometimes is:

| Qualifying departures in-window | Matched records |
|---|---|
| 1 | 11,846 |
| 2 | 462 |
| 3 | 17 |

For **479 records**, more than one qualifying departure by the correct vessel
fell inside the window and `pick_event()` chose by nearest-offset heuristic
(ties toward the later date, then lowest `event_key`). A wrong pick attributes
tonnage to the wrong sailing — it does not attribute it to the wrong ship. The
published claim is defensible as written; this is a precision note, not a
defect.

## 3. Claim 2 — No fuzzy matching — **CONFIRMED**

> *No fuzzy matching anywhere. "DSI Phoenix" and "DSL Phoenix" are different real vessels and must never merge.*

### Exhaustive search for fuzzy machinery

The three scripts, `lib/parse.py` and both SQL schema files were searched for:
`levenshtein`, `difflib`, `SequenceMatcher`, `get_close_matches`, `fuzz`,
`rapidfuzz`, `thefuzz`, `jellyfish`, `jaro`, `soundex`, `metaphone`,
`editdist`, `similarity`, SQL `LIKE` / `ILIKE` / `~~` / `regexp` on names, and
prefix matching via `startswith` / `endswith` on names.

**Result: zero hits.** The only `startswith` in the codebase is
`ship_type_group.startswith("Bulk Carrier")`, on a *ship-type* string, not a
vessel name. Every name comparison in the system is exact equality (`==`),
set membership (`.isin()`), or a dict key lookup on the normalized string.

### Every matching path enumerated

| # | Path | Comparison | Fuzzy? |
|---|---|---|---|
| 1 | FGIS carrier → vessel (`resolve`) | dict lookup on `(date, normalized_name)` | No |
| 2 | Corrupted-IMO repair (`build_imo_repair_map`) | exact normalized-name grouping | No |
| 3 | Dredge exclusion by name | `.isin(set of normalized names)` | No |
| 4 | Vessel identity fallback (`natural_vessel_key`) | `'NONAME:' + name.strip().upper()` | No |
| 5 | Alias dedup within a vessel | exact normalized-name equality | No |

### The specific pair

```
normalize_vessel_name('DSI Phoenix')    -> 'DSIPHOENIX'
normalize_vessel_name('DSL Phoenix')    -> 'DSLPHOENIX'
normalize_vessel_name('D.S.L. Phoenix') -> 'DSLPHOENIX'
```

`DSIPHOENIX != DSLPHOENIX` under every one of the five paths above. There is
no code path in which a one-character difference can bridge them.

In this dataset `DSL Phoenix` does not appear at all. `Dsi Phoenix`
(IMO 9738337) appears with 20 events and matched 3 FGIS records
(2025-12-14, 2026-01-01, 2026-01-02), all correctly and all on the sailing.
21 distinct `*PHOENIX*` vessels exist in `dim_vessel_name_alias`; none share a
normalized name.

### Adjacent finding — `str.replace()` is not used for editing

The audit brief flagged `str.replace()` as a risk. It is not used for text
editing anywhere. The three `.replace()` calls are pandas whole-value
replacements (`Series.replace("", None)`, `regex=False` by default), which
substitute the empty-string *value* and cannot touch substrings.

## 4. Claim 3 — The 31 corrupted-IMO merges — **WRONG (1 of 31)**

> *31 corrupted-IMO merges are all correct. Each merged pair must be one physical ship.*

30 of 31 are defensible. **One is provably wrong.**

### 4.1 The named guard cases — confirmed correct

| Vessel | Outcome | Detail |
|---|---|---|
| **Aquitania** | ✅ Separate | 9300491 (37 events) and 9611278 (42 events) both retained; both check-digit valid |
| **Sea Voyager** | ✅ Separate | Four vessels: 9408310 (Tanker), 9799707 (Bulk), 9408762 "Seavoyager" (Tanker), and 8945819 — check-digit **invalid** and correctly *not* merged, because two valid twins exist |

### 4.2 H1 — `1782585 -> 9747120` ("Egret") is a false merge

**This is the largest of the 31 merges: 131 of the 256 repaired rows (51%).**

IMO 9747120's own name history in the source data:

| Name carried | Rows | Period | Type | Agents |
|---|---|---|---|---|
| Nord Oceania | 28 | 2020-07-18 → 2025-08-22 | Tank | Gulf Harbor, Inchcape, Transmarine |
| **Egret** | 9 | **2026-01-01 → 2026-01-09** | Tank | Gulf Harbor, Inchcape |

The 131 merged rows (raw IMO `17825854`, truncating to `1782585`) run
**2019-01-03 → 2019-10-21** — before the tanker carried that name, and before
the tanker appears in the dataset at all. Their profile is a resident
workboat, not an ocean ship:

| Signal | Merged 2019 rows | Real tanker 9747120 |
|---|---|---|
| River miles | 226–232 only (6-mile band) | Full river |
| `Enter` / `Exit` (pilot station) | **Zero — never enters or leaves the river** | Present |
| Draft recorded | **0 of 131 rows** | 27–42 ft |
| Agent recorded | **0 of 131 rows** | Gulf Harbor / Inchcape / Transmarine |
| Type recorded | **0 of 131 rows** | Tank |
| IMO digit distance | **7 of 7 digits differ** — not a typo pattern | — |

Zone distribution of the merged rows: `Baton Rouge Gen Anch` 51,
`Apex Baton Rouge` 30, `Meal Anch` 24, `Genesis Baton Rouge` 10,
`Placid Oil` 8, `Dreyfuss` 4, `Drax Biomass` 2, `Baton Rouge General Cargo` 2.

**Consequence in the built warehouse:** vessel 9747120 carries 168 events, of
which **131 (78%) belong to a different vessel**. 28 of its 32 fee-bearing
sailings — **$98,000 of its $112,000** — are the workboat's 2019 berth
departures, every one of them on a row with no agent recorded.

No FGIS contamination resulted (no FGIS carrier normalizes to `EGRET`), but
the merged workboat did depart `Dreyfuss`, an Elevator, twice — so it entered
the grain-match candidate pool under the tanker's identity.

### 4.3 Why the guards did not catch it

`build_imo_repair_map` merges when a normalized name has **exactly one
check-digit-valid IMO**. A *second real vessel whose IMO is also corrupt* is
invisible to that test — it contributes no valid IMO, so the "exactly one"
condition still holds. The three documented guards (one-valid-twin,
dredge-name exclusion, type-conflict) do not address this case.

### 4.4 The other 30 — evidence reviewed

Each merge was profiled on: digit distance and typo shape, overlap between the
corrupted rows' dates and the period the good vessel actually carried that
name, agent continuity, type continuity, zone overlap, and whether the
corrupted rows constitute a complete `Enter` → berth → `Exit` river call.

| Class | Count | Assessment |
|---|---|---|
| Single glitched row inside the good vessel's active window, same agent, same type | 24 | Correct |
| Non-overlapping name window, but a complete ocean river call and a 1–2 digit / transposition IMO relationship | 6 | Defensible |
| **Non-overlapping window, no river call, no draft/agent/type, 7-digit distance** | **1 (Egret)** | **Wrong** |

Strongest positive example: `9139229 -> 9139294` ("Happy River") — the raw
value is `91392294`, which is the correct IMO `9139294` with one duplicated
digit; truncation to seven characters then produces the wrong value. Same
agent (Norton Lilly), same type (Bulk). Unambiguously one ship.

Suggested discriminator (not implemented — audit is read-only): refuse the
merge when the corrupted-IMO rows contain no `Enter`/`Exit` event **and** their
date range does not overlap the period the good vessel carried that name.

## 5. Claim 4 — Agency fee — **WRONG (double-counting)**

> *$10,500 for bulk, $3,500 otherwise, only on Depart from a non-anchorage/non-pilot berth. NULL means no fee accrues. Verify no double-counting and no berth sailing wrongly priced or skipped.*

### 5.1 What is correct

The code implements the **stated rule exactly**. No fault was found against
the specification as written.

| Test | Result |
|---|---|
| `agency_fee` non-NULL outside `Depart` at a berth | **0 rows** |
| Non-berth departures (Anchorage / Pilot Station) priced | **0 of 56,921** |
| Distinct fee values in the fact table | **2** ($3,500 / $10,500) |
| Priced sailings / total | **48,167 / $349,625,500** |
| Zones with NULL `facility_type` (would be silently skipped) | **0 of 215** |
| Rows where the rate disagrees with `vessel_type_canonical` | **0** |
| Under-billing via the ships-register fallback | **2 departures** — negligible |

Nothing is skipped for a missing zone classification, and no row is priced at
a rate inconsistent with its vessel type.

### 5.2 H2 — The fee is charged per berth departure, not per port call

Segmenting `fact_zone_event` on `Enter` (pilot-station) events to delimit port
calls:

| Charges within one port call | Calls |
|---|---|
| 1 | 31,025 |
| 2 | 5,667 |
| 3 | 1,144 |
| 4 | 313 |
| 5 | 86 |
| 6–10 | 61 |
| **Total fee-bearing calls** | **38,296** |

**7,271 calls (19.0%) are charged more than once.**

| Basis | Amount |
|---|---|
| Booked inside call boundaries (47,899 charges) | $347,602,500 |
| One charge per call, keeping the highest tier | $280,343,000 |
| **Excess attributable to multi-berth charging** | **$67,259,500 — 19.2% of the published total** |

A further 268 charges ($2,023,000) precede any `Enter` event in their vessel's
history and cannot be attributed to a call at all.

**Worked example** (vessel_key 287, one `Enter`→`Exit` call, Sep–Oct 2022):
`Stolthaven 3` → `Dow Missouri` → `Dow Taft`, three separate $3,500 charges
between a single river entry and a single river exit.

### 5.3 The indefensible subset — same berth, minutes apart

**179 charges ($1,746,500) are a second charge at the *same zone* within 60
minutes of the first:**

| Vessel | Zone | Previous | Charged | Gap | Fee |
|---|---|---|---|---|---|
| Bold Guardian | Meraux Buoys Lower | 2020-04-27 08:27 | 08:28 | 1 min | $10,500 |
| Fpmc 27 | Dow Missouri | 2019-06-08 19:28 | 19:29 | 1 min | $3,500 |
| Artvin | ADM Destrehan Buoys Upper | 2020-12-15 15:19 | 15:21 | 2 min | $10,500 |
| Mazowsze | 175 Buoys | 2025-03-06 09:09 | 09:11 | 2 min | $10,500 |
| Oslo Bulk 6 | Harmony St | 2025-12-05 06:01 | 06:03 | 2 min | $10,500 |
| Santos Eagle | Meraux Buoys Upper | 2022-03-27 20:33 | 20:35 | 2 min | $10,500 |

Widening the window: 186 charges within 6 h ($1,799,000), 267 within 24 h
($2,439,500), 586 within 72 h ($5,271,000).

These survive deduplication because the dedup key
`(natural_vessel_key, action, Time, zone_name)` requires an **exact** timestamp
match; rows one minute apart are treated as distinct events.

### 5.4 The project's own evidence contradicts the rule

`docs/PORT_CALL_EVIDENCE.md` line 91, derived from four real Statements of
Fact, states the governing principle:

> **Shifting within a berth is not a second berth call.** Ultra Leopard shifted
> forward and aft at ADM-Reserve several times over the loading (tugs, lines
> re-made, pilot on/off each time) without ever leaving the berth. Assembly
> must not read these as separate stops.

The agency-fee logic reads them as exactly that. Whether the fee is
contractually per port call or per berth departure is a commercial question
the audit cannot settle — but the two documents currently disagree with each
other, and $67.3M sits on the difference.

### 5.5 M5 — "NULL means no fee accrues" is documented with the wrong vessels

`DATA_QUALITY.md` states the 3 unpriced berth sailings are *"Dixie Raider,
Jesse A Mollineaux, Usace Mat Sink Unit, French Warship, Cg Eagle, 'Shop'"*.
That sentence is hardcoded in `build_db.py` and is now **impossible** — all six
are on the exclusion list and cannot reach `fact_zone_event`.

The actual three:

| Vessel name | Zone | Facility | Time |
|---|---|---|---|
| Carnival Valor Rb2 | Erato St | Cruise | 2024-10-19 15:57 |
| Ncl Escape Rb Sb | Julia St | Cruise | 2025-12-07 16:36 |
| Ncl Escape Rb Sb | Julia St | Cruise | 2025-12-07 17:14 |

`Carnival Valor Rb2` is the *same physical call* as Carnival Valor
(IMO 9236389) at Erato St that day — the real ship arrived 05:35 and departed
16:53. So the semantics claimed ("NULL means *no fee accrues*, not
*unknown*") are false for these rows: they are unidentified name-variant
artifacts of a call that was already charged. The dollar outcome happens to be
correct — charging them would double-count — but for the opposite reason to
the one documented.

### 7.5 H3 — `--keep-dredges` merges the Texas Star dredge into the real tanker

The documented retention flag triggers the exact failure the code claims to
guard against.

```
$ python3 scripts/build_db.py --keep-dredges
Repaired 32 corrupted IMO(s) affecting 2,645 rows:
    ...
    3110000 -> 9256860        <-- dredge MMSI 311000000, truncated
    ...
```

| Build | Events on 9256860 | Chargeable sailings | Agency fees |
|---|---|---|---|
| Default | 20 | 3 | **$10,500** ✅ |
| `--keep-dredges` | 2,397 | 1,125 | **$3,937,500** ❌ (375×) |

**Root cause.** In `load_dredge_exclusions`, a name is added to the
`names` set **only in the `else` branch — when the dictionary entry has no
usable IMO**:

```python
imo = canonical_imo(r.get("imo_raw", "").strip())
if imo:
    imos.add(imo)
else:
    names.add(normalize_vessel_name(name))
```

Texas Star has `imo_raw = 311000000` → canonical `3110000`, so `"TEXASSTAR"`
**never enters `excluded_names`**, and guard #2 in `build_imo_repair_map`
never sees it. In the default path this is masked because the dredge rows are
filtered out *before* the repair map is built. With `--keep-dredges`,
`dredge_exclusions` is `(set(), set())`, so the row filter **and** the name
guard disappear together.

As written, guard #2 can never fire for any IMO-bearing dictionary entry.

## 9. Low-severity and latent findings

| ID | Finding |
|---|---|
| **L1** | **Guard #2 in `build_imo_repair_map` is effectively dead.** Beyond H3: in the default path the dredge rows are already filtered before the repair map is built, so the excluded names have no IMOs left to protect. |
| **L2** | **`normalize_vessel_name(nan)` and `canonical_imo(nan)` raise `AttributeError`.** Unreachable today — all callers feed `.str.strip()` output from `keep_default_na=False` reads. The `isinstance`-guarded call sites (`agency_fee_for`, `build_imo_repair_map`) were probed directly with `NaN` in every argument position and behave correctly; the two documented NaN bugs do not recur. |
| **L3** | **`fgis_record_id` PK collision is reachable on the NONAME path.** The schema comment claims uniqueness "by construction" via `(imo, cert_date)`, which holds only when `imo` is non-NULL. Two no-IMO vessels differing only in punctuation (`ABC-1` / `ABC 1`) have distinct `natural_key`s but one normalized name; matching both on the same cert date yields a duplicate primary key. Two matched records currently take this path (`Strategic Savannah`, `Sakura L`); no collisions exist today. |
| **L4** | **"The build verifies that no fallback record had a sailing available" is false as stated.** BUILD.md, CHANGELOG and the printed `FGIS_MATCH_QUALITY.md` line ("Verified on every build: **zero**") are hardcoded prose. No verification code exists. The property is true and holds structurally — `resolve()` reaches the fallback only when the departure lookup returns nothing — and the audit confirmed it by independent query, but nothing is checked at build time. |
| **L5** | **`groupby(["name_normalized","cert_date"])` drops `NaT` keys**, after which Phase 2's `resolutions[...]` lookup would raise `KeyError`. Not triggered: 0 rows with NULL `cert_date_parsed` or blank `carrier_name`. |
| **L6** | **`g_sorted.iloc[-1]`** selects a vessel's latest name/IMO after `sort_values("event_time")`, which places `NaT` **last** — a single unparseable timestamp would make that row define the vessel's identity. `bad_timestamps` is 0, so unreached. |
| **L7** | **The alias join in `load_candidates` is time-unbounded** — a berth event is indexed under every name the vessel ever carried, regardless of when. This is what makes rename-matching work (11 matched records rely on it legitimately, e.g. `ATLANTICISLAND` 2019 certs against a name MRTIS first records in 2020), but it is also how a wrong twin could be selected when the right one has a missing berth event. |
| **L8** | **185 normalized names are shared by more than one `vessel_key`**, 136 of which appear as FGIS carrier names. Date-and-zone narrowing disambiguates all but one (`AQUITANIA`). Inherent to name-only matching, not a defect — but it is the precision surface. |
| **L9** | **`"Gen"` (general cargo, 16,752 rows) maps to `Bulk`** in `vessel_type.csv`, so general-cargo ships bill at $10,500 and are reported inside the "Bulk" row of the fee table. Probably intentional given BUILD.md's General Cargo discussion, but it is stated nowhere. |
| **L10** | **Dead expression** in the fee-table row builder (`build_db.py`): `${row['count'] and fee['agency_fee'].max() if False else ''}` always evaluates to `''`. |

## 11. Recommended remediation order

| Priority | Finding | Rationale |
|---|---|---|
| **1** | **H1 — Egret false merge** | Corrupts a real vessel's identity, misattributes 131 events and fabricates $98,000. A targeted guard (no `Enter`/`Exit` in the corrupted rows **and** no overlap with the good vessel's name window) would catch it without disturbing the other 30. |

| **3** | **H3 — `--keep-dredges` guard** | One-line fix in `load_dredge_exclusions`: add the normalized name to `names` for **every** excluded entry, not only those without an IMO. |
